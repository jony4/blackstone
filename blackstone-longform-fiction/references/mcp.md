# 增值服务与 MCP 工作流

## 云端操作模式

连接云端不等于同意上传或付费调用。模式保存在 `~/.blackstone/preferences.json`：

```json
{"cloud_sync_mode":"ask"}
```

只接受两个值：

- `ask`：每次询问，默认值。每组付费云端操作前，用作者能理解的话说明准备读取或上传什么、会执行哪些动作，以及成功调用按 0.01 元/次计费；得到明确同意后才调用。
- `auto`：自动同步。只有作者明确选择后才能写入。作者确认的正文和六项资料可以按闭环保存并维护图谱，完成后报告实际动作和调用结果。

文件不存在、内容无效或读取失败时一律使用 `ask`。作者说“每次问我”“关闭自动同步”时写为 `ask`；作者明确说“开启自动同步”时写为 `auto`。不要从沉默、继续写作或确认正文推断作者同意上传。

无论采用哪种模式，下面三类操作都必须单独确认：

1. **推断、计划或候选方案**——正文里没有发生过的事；
2. **覆盖或撤回已有事实**——把已有节点、关系或资料改成另一个说法；
3. **涉及剧情走向的决定**——由作者决定，不由检查结果代劳。

查询余额、账单和提交已获同意的反馈不收费，按对应流程直接执行。身份验证、配置写入和支付仍遵守 [account.md](account.md) 的单独授权边界。

## 核心职责

远端服务保存作品资料、章节正文和作品级故事图谱，为跨会话召回、事实核对、连续性检查及跨客户端写作提供支持。

正文是作品事实的最高依据。故事图谱用于组织和召回事实，不取代正文，也不属于某一章。

## 资源层级

每次调用都传入 `edition: longform-fiction`。除 `story_list` 和 `story_create` 外，还必须传入 `story`。

```text
story（作品，聚合根）
├── volume（分卷，按 ordinal 排序）
│   └── chapter（章节，按全书 chapter_number 排序）
├── facet（六项作品资料）
└── graph（该作品独立拥有的一张故事图谱）
    ├── node
    └── relation
```

章节可以成为图谱节点、关系和事实的证据来源，但图谱始终按 `story` 隔离，不挂在单个章节下面。

## 命名规范

所有公开工具使用 `resource_action`：

- 查询集合用 `_list`；读取单项用 `_get`；
- 新建聚合根用 `_create`；
- 可重复创建或更新用 `_upsert`；
- 更新已有聚合根用 `_update`；
- 写前准备、上下文召回和检查分别用 `_prepare`、`_context`、`_check`；
- 从规范正文刷新作品图谱用 `graph_sync`。

不要猜测旧工具名，不要把 REST 路径、底层图引擎命令或历史别名当作 MCP 工具。

## 工具清单

### 作品、分卷与章节

- `story_list`：列出作品。
- `story_create`：创建作品，可同时创建初始分卷。
- `story_get`：读取作品、分卷、章节、六项资料和图谱覆盖。
- `story_update`：更新标题、标语和立意摘要。
- `volume_list`：列出分卷。
- `volume_upsert`：按 `ordinal` 创建或更新分卷。
- `chapter_list`：列出章节；只有确实需要时才包含全部正文。
- `chapter_get`：按全书章节编号读取一个章节。
- `chapter_prepare`：写作前从整部作品准备相关正文、计划、规则和图谱事实。
- `chapter_context`：读取指定章节及相邻章节、人物和未完成线索。
- `chapter_check`：保存前检查草稿与整部作品的连续性。
- `chapter_upsert`：把确认正文保存到指定分卷，随后默认回读核验并刷新作品图谱。

### 六项写作资料

- `facet_list`：读取全部六项资料。
- `facet_get`：读取一项资料。
- `facet_upsert`：保存一项作者已经确认的结构化资料并回读核验。

六项技能与 `kind` 一一对应：

| Skill | kind | 必须遵循的内容逻辑 |
|---|---|---|
| 立意 | `premise` | 核心设问、新鲜度、吸引力、展开能力和验收结果 |
| 人物 | `characters` | 三个维度、经历到选择的因果链、关系、弧光和验收结果 |
| 主题 | `theme` | 主题领域、主题问题、人物立场、弧光连接、故事证明和验收结果 |
| 故事结构 | `structure` | 核心冲突、四部分、三次转折、两次压力、高潮、因果回收和验收结果 |
| 场景设置 | `setting` | 结构位置、使命、视角、目标、阻力、风险、环境、转折、结果和后续因果 |
| 写作风格 | `style` | 读者、视角、三种声音、表达规则、调整目标和验收结果 |

只保存对应 Skill 已经完成且经作者确认的输出。候选方案、助手推断和未来计划不得静默写成既定资料。

### 账户、账单与反馈

这三个工具不属于任何一部作品，**一律不扣费**：

- `account_status`：余额和单价。
- `account_recharge`：换一个免登录的付款页地址，直接用系统命令打开；30 分钟内有效。
- `account_usage`：账单流水，每笔扣费对应哪个工具、多少钱、什么时候。
- `feedback_submit`：代作者提交一条反馈，必须先征得同意。

作者问余额、问账单、想反馈时直接调用，不要把他推到网页去。详见 [account.md](account.md) 和 [feedback.md](feedback.md)。

### 作品级故事图谱

- `graph_sync`：从该作品全部分卷和章节刷新规范图谱视图。
- `graph_overview`：读取图谱版本、节点类型和状态覆盖。
- `graph_query`：在当前作品内部查询节点和关系。
- `graph_node_upsert`：批量维护已审核节点。
- `graph_relation_upsert`：批量维护已审核关系。

### 节点类型与状态（写错会被服务端拒绝）

`kind` 只能取这 12 个值，不要自造：

`chapter`、`character`、`location`、`faction`、`event`、`fact`、`thread`、`theme`、`world_rule`、`item`、`relationship`、`plot`

`status` 只能取：`asserted`（正文已发生）、`planned`（计划中）、`inferred`（推断）、`retracted`（已撤回）。默认用 `asserted`，因为沉淀的应当是正文里已经发生的事。

`id` 只能用字母、数字和 `.` `_` `:` `-`，以字母或数字开头，最长 160 字符。**不要用中文做 id**，用 `character.chen-jiu` 这样的形式，中文放在 `name` 里。

写入被拒时，服务端会指明是第几个节点的哪个字段、期望什么。**照着改，不要原样重试**——`_upsert` 属于写入类，重复提交同一份非法数据只会重复失败。

图谱节点和关系必须使用稳定 ID。修订同一事实时复用 ID；撤回或废弃事实时更新 `status`，保留来源与演变记录，不通过创建重复节点规避冲突。

## 六项资料闭环

1. 用 `story_get` 确认作品及记忆覆盖。
2. 用 `facet_get` 读取当前任务对应资料；需要跨项检查时再用 `facet_list`。
3. 读取对应 Skill 文件，严格按其引导顺序、输出格式和验收标准完成分析。
4. 区分正文事实、已确认资料、候选方案和助手推断。
5. 由作者确认本轮结论。
6. 按云端操作模式处理保存：`ask` 模式先取得本组操作同意；`auto` 模式可在内容确认后执行 `facet_upsert`。
7. 检查返回的回读核验结果；失败时不得声称已保存。
8. 若资料改变人物、事件、规则或故事承诺，再更新相关图谱节点和关系，并用 `graph_query` 核验。

## 新建作品闭环

创建云端作品属于付费写入。`ask` 模式必须先说明要创建作品并取得同意；`auto` 模式可以在作者确认第一项可用结论后创建。

1. `story_list`：确认不是重复作品。
2. 用立意 Skill 形成并确认最低可用立意。
3. `story_create`：创建作品和至少一个初始分卷。书名未定就用作者的说法或立意里的短语作为临时标题，之后 `story_update` 改即可——不要为了等一个正式书名而卡住整条流程。
4. `story_get`：核验作品层级。
5. 按作者当前进度逐项完成六项技能；不要为了填满资料而生成未经确认的内容。
6. 每项确认后按当前模式处理 `facet_upsert`；`ask` 模式可以把同一轮明确列出的多项保存合并为一次授权，但不得把授权扩展到之后的轮次。
7. 建立人物、规则、结构节点等必要图谱记忆后，分别执行图谱 upsert 和查询核验。

## 章节写作与续写闭环

先完成本地写作；需要读取或写入云端时按当前云端操作模式取得授权。

1. `story_get`：确认作品、目标分卷和目标章节编号。
2. `volume_list`、`chapter_list`：层级不明确时核对卷章位置，禁止把章节写入错误分卷。
3. `facet_list`：读取六项资料；只采用作者确认的资料。
4. `chapter_prepare`：按写作意图准备整部作品中的相关正文、规则、计划和图谱事实。
5. 必要时用 `chapter_context` 或 `graph_query` 缩小召回范围。
6. 按故事结构 Skill 确认阶段任务，按场景设置 Skill 确认场景使命、人物行动、转折结果和后续因果。
7. 按人物、主题和写作风格 Skill 完成正文，并以本地最新正文为最高依据。
8. `chapter_check`：检查事实、人物状态、时间、数值、命名、格式、伏笔和卷章连续性。
9. 修正阻断问题；涉及剧情决定时等待作者确认。
10. 按本地文件管理规范写入正文并重新读取关键位置。
11. 按云端操作模式决定是否执行 `chapter_upsert`；执行时保存同一份确认正文到正确分卷，并完成回读核验和作品图谱刷新。
12. 检查 `verified` 和图谱刷新结果；不明确时先 `chapter_get` 回读，不盲目重复写入。
13. 从刚保存的正文里提取已经发生的事实；`ask` 模式只有在本组授权已明确包含图谱写入时才执行，`auto` 模式可以执行。不要把推断或计划写成已发生事实。
14. 用 `graph_query` 或 `graph_overview` 核验图谱版本和关键事实。
15. 明确报告本地文件、云端章节、图谱分别是否完成并核验。

## 修改与润色闭环

1. `chapter_get` 和本地文件共同确认最新正文；冲突时以本地正文为准并展示差异。
2. 按作者要求选择人物、场景或写作风格 Skill，不擅自扩大修改范围。
3. 若只修改表达，保留情节、动机、关系、线索、世界规则和场景结果。
4. 执行 `chapter_check`。
5. 作者确认后更新本地正文。
6. 按云端操作模式决定是否执行 `chapter_upsert`，执行后核对回读及图谱刷新结果。
7. 只有作品事实发生变化时才更新图谱节点或关系；纯措辞变化不制造新的故事事实。

## 连续性与图谱维护闭环

1. `graph_overview`：确认覆盖和版本。
2. `graph_query`：针对人物、关系、事件、时间、物品、地点或伏笔进行有界查询。
3. `chapter_context` 或 `chapter_get`：回到正文证据。
4. 区分正文事实、推断、计划和已撤回事项；正文冲突必须展示。
5. 提出待维护节点与关系的准确变更，涉及覆盖或撤回时等待作者确认。
6. 用稳定 ID 执行 `graph_node_upsert` 或 `graph_relation_upsert`。
7. 再次 `graph_query`，确认内容、状态、来源和关系方向正确。
8. 需要全书规范视图时执行 `graph_sync`，随后读取 `graph_overview`。

## 计费、失败与安全重试

逐个工具的收费明细见 [pricing.md](pricing.md)。Web 工作台和 REST 管理接口不计费。仅成功的 MCP 业务工具调用扣 0.01 元；失败调用以及 `initialize`、`ping`、`tools/list`、`notifications/*` 不扣费。余额不足或工具不可用时，六项写作技能和本地正文仍可继续，但必须标记为降级完成。

调用返回 `unauthorized`（尚未授权本机）或 `insufficient_balance`（余额用完）时，读取 [account.md](account.md)，按其中的流程和话术处理，不要把原始错误码或技术名词抛给作者。每次成功调用的响应头 `X-Blackstone-Balance` 带有当前余额（单位是元），低于 0.50 元时按该文件的规则追加一次充值提醒。

- 临时失败的只读工具最多自动重试一次。
- 身份验证、权限和参数错误不得自动重试。
- `_create`、`_update`、`_upsert` 和 `graph_sync` 不得盲目重试。
- 写入超时后先用对应 `_get`、`graph_query` 或 `graph_overview` 核验。
- 不在回复、Skill 或配置中展示完整访问凭证。

## 完成反馈

每次远端任务结束后明确说明：

1. 操作的是哪个作品、分卷和章节范围；
2. 使用了哪项写作资料和图谱范围；
3. 本地正文、云端正文和图谱分别是否已保存；
4. 写入是否完成回读核验；
5. 是否发现正文、资料和图谱冲突；
6. 当前状态是已完成、部分完成、结果不确定还是已降级完成。
